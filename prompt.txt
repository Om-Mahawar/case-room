CASE ROOM: CLAUDE CODE PROMPTS, STAGE BY STAGE

How to use: start Claude Code in the unzipped case-room folder. Use one fresh session per stage.
Paste everything between the START and END lines of a stage. Do not move on until its gate is met.

STAGE 3: INTERVIEW ENGINE (LOGIC ONLY)
==============================================================================
BEFORE YOU PASTE: nothing.

----- START OF PROMPT -----
Read CLAUDE.md, prompts/interviewer.md, src/engine/numbers.ts, src/engine/skeletonView.ts,
src/schema/skeleton.ts, and sections 7.2, 7.3, 8, 9.3, 10.1 and 12 of docs/BRD-engineering.md.
Read docs/DECISIONS.md: the number check is stricter than the spec, and that is intended.

Build the interview engine as pure TypeScript with no React, driven entirely by tests against
MockClient. No screen in this stage.

Write the tests first; they are the specification.

1. Session state: Ready, Interviewing, Closing, Grading, Scored, plus Paused and NotScored.
   A reducer (or equivalent) moves between them. Record on each session: skeleton id and
   version, prompt version, model ids, app version, messages, ledger, usage.
2. Ledger: turn number, facts revealed, nudges used, wrong turns seen, crux reached, close
   issued, running note. Updated only from a valid InterviewerTurn; a fact id that is not in
   the skeleton is ignored; nudges are capped at two.
3. Prompt builder (spec 10.1): rules, skeleton view, style line, ledger, last six messages.
   Older messages are not sent.
4. One turn (spec 7.3), exactly in that order. In particular:
   - BR-1: the opening prompt is the skeleton's prompt, with no model call.
   - BR-4: run the number check on every reply. On failure regenerate once, naming the
     number; on a second failure replace the reply with the out-of-scope sentence. At most
     two regenerations per session.
   - BR-11: trim a reply over 120 words.
   - BR-12: pass a warning to the model at turn 12; after the last budgeted turn the engine
     issues the closing prompt itself with no model call. Drills use 6 turns, full cases 14.
     "Wrap up now" issues the closing prompt immediately.
   - BR-13: after the recommendation the engine prints "Thanks, that's all I need." with no
     model call and moves to Grading.
   - INT-9: if the reply is not valid JSON, show its text and leave the ledger unchanged.
   - INT-8: on a limit or network error the session moves to Paused and loses nothing.
5. A hard cap of 18 requests per case, enforced in the engine.
6. Tests: every rule above; a stalling candidate reaches the closing prompt at exactly the
   budget (T-END); a bad reply is caught and replaced (T-NUM); a session serialised to JSON
   and restored continues at the same turn (T-RES); request and token totals are recorded
   (T-BUD on mock data).

Do not change the skeleton JSON files or prompts/interviewer.md in this stage. If a rule in the
spec is ambiguous, stop and ask rather than guess. Show me the test list before writing the
engine. Finish with npm run check passing, a commit, and docs/PROGRESS.md updated.
----- END OF PROMPT -----

GATE: engine tests pass; no React import anywhere under src/engine.

----- START OF PROMPT -----

docs/BRD-engineering.md.

Prove the interviewer keeps the rules on the real model, and tune the prompt until it does.

1. tests/fixtures/rule-probes/: for each of the 16 skeletons, generate scripted candidate

   and report: do not loosen a pass mark, and do not move a rule from code to the prompt.
   The fallback in the spec (risk R3) is to try the larger Flash model; tell me the cost in

STAGE 6: GRADER, SCORECARD, HISTORY
==============================================================================
BEFORE YOU PASTE: nothing.

----- START OF PROMPT -----
Read CLAUDE.md and sections 8 (BR-14 to BR-16), 9.4, 10.2, 12.3 and 13 of
docs/BRD-engineering.md.

Build grading.

1. prompts/grader.md (version 1): the five dimensions, BR-14 to BR-16, the "you said / say
   instead" format with the word limits in section 12.3, and the anchor-band method of
   section 13.2. The grader is given the whole skeleton including anchors and answerKey, the
   final ledger and the full transcript with turn numbers. It never sees casebook text.
2. A zod schema for Scorecard (section 12.3), with the JSON schema the model call needs.
3. Grading flow (GRD-1, GRD-2): one request on the grader model; validate; on failure retry
   once; then fall back to the interviewer model; then NotScored with the transcript kept.
4. The band clamp in code (section 13.2, step 4): the overall score must sit in its band's
   range; clamp and record that it was clamped.
5. Quantitative reasoning is "not assessed" (null) when the skeleton has no numeric fact and
   no quant moment; synthesis is not assessed when the session ended without a
   recommendation. The overall score ignores unassessed dimensions.
6. INT-10: a session with fewer than three candidate turns is not graded.
7. Scorecard screen (GRD-3 to GRD-5): overall and five scores, each with evidence, "you
   said" and "say instead"; the priority; the practice plan; the best moment; every score
   labelled "AI estimate"; then, and only then, the case's crux, valid paths and source page.
8. Save scorecards in IndexedDB keyed by session. A scorecard is never regraded against a
   newer skeleton version.
9. Tests with MockClient: valid scorecard; invalid then valid; fallback; clamp; unassessed
   dimensions; too-short session; the guesstimate rule (a sound method with a far-off final
   figure is not marked down for the figure).

Show me the grader prompt and the plan before building the screen. Finish with npm run check
passing, a commit, and docs/PROGRESS.md updated.

STAGE 9: DRILLS
==============================================================================
BEFORE YOU PASTE: nothing.

----- START OF PROMPT -----
Read CLAUDE.md and section 9.5 of docs/BRD-engineering.md.

Build the three drills. Every drill draws only on skeleton content; nothing is generated.

1. Structure sprint (DRL-1): a skeleton's prompt, 2.5 minutes, the student writes a
   structure; one grader request scores it against the skeleton's valid paths.
2. Math sprint (DRL-2): a skeleton's quant moment with its inputs, 4 minutes; the answer is
   checked in code against the stored working, with a sensible tolerance; no model call.
   Only skeletons with a quant moment that is not optional are used.
3. 60-second synthesis (DRL-3): the facts of a case, 90 seconds; one grader request scores
   the recommendation against the crux and the close.
4. DRL-4: a drill never uses a case the student has not already played in full.
5. Save results; they feed the progress statistics. The scorecard's practice plan links to
   the matching drill.

A drill costs at most one request. Show me the plan first. Finish with tests, npm run check
passing, a commit, and docs/PROGRESS.md updated.
----- END OF PROMPT -----

GATE: each drill runs on a case you have already played.
